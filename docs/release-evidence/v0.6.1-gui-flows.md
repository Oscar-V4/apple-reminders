# v0.6.1 GUI-backed user-flow verification

This is the 2026-09-05 follow-up to v0.6.0, performed with the actual macOS
Reminders app through Computer Use and the packaged Core MCP over stdio.
It records synthetic test data only. Initial observations use the installed
v0.6.0; the final section records the signed v0.6.1 candidate verification.

## Environment and scope

- macOS 26.5.2, Apple Silicon; Reminders build 3976, Korean UI.
- Existing Reminders authorization and iCloud account on the development Mac.
- Four isolated lists with the `Codex GUI QA` test prefix: one main list, two
  identically named lists, and one destination list. Existing user tasks were
  not changed. No accounts, system timezone, permissions, or sharing changed.
- GUI actions used Computer Use accessibility targets and screenshots. Plugin
  actions used the actual bundled launcher and signed EventKit helper. No
  direct database writes or private extension fallbacks were used.
- GUI screenshots were inspected in the task. Personal sidebar content was
  hidden for test-item inspection and is not included in repository artifacts.
- This does not establish fresh-user TCC behavior, minimum macOS 14 support,
  iPhone visibility, notification delivery, or iCloud convergence.

## Baseline findings and regression scenarios

| Flow | Observed behavior and decision |
| --- | --- |
| GUI-created Korean/emoji title → Core read | Exact text returned, including composed family emoji in later notes. Computer Use keystroke input initially dropped non-ASCII; setting the actual editable field resolved the automation issue. This was not a plugin defect. |
| Core multiline notes, note link, priority → GUI | All three note lines, clickable visible note link, and medium priority appeared. Public EventKit URL metadata was returned by Core but did not populate the GUI URL/attachment field; this remains an explicit boundary. |
| GUI title edit after Core exact read | Old-reference patch rejected before writing. Fresh read preserved the manual title, notes, and priority. |
| Two same-name lists in the same account | v0.6.0 returned an arbitrary first ID with a duplicate warning. Modified facade rejected both a fresh request and the old persisted receipt replay as `ambiguous_scope`, with no selected list. |
| Page read → GUI recurring completion → next page | Cursor rejected as `pagination_snapshot_stale`; restart required. |
| GUI recurring completion | Original ID became the next incomplete occurrence and a new ID represented the completed occurrence. The app displayed the advanced date and completed history separately. |
| Core recurring completion | v0.6.0 advanced the original ID again, then returned verification pending. The fix blocks this action before dispatch; the user can complete the intended occurrence once in the app. Retrying the original ID is unsafe. |
| Same-title reminders with distinct notes A/B | Completing exact A left B incomplete in the GUI. Showing completed reminders displayed A and B in their respective states. |
| GUI reopening exact A | Core read returned A incomplete; B stayed unchanged. |
| GUI deleting exact B → old-reference mutation | Rejected before writing; exact read returned `not_found`. A remained present. No title-based substitution or resurrection occurred. |
| Move exact A to another list | Core returned the exact destination and preserved A's note. The destination GUI showed exactly A and its note, and the original list no longer showed A. |
| First all-day due on a previously unscheduled item | The app stored the requested date, but also synthesized a floating midnight start. v0.6.0 reported a verification mismatch. The fix accepts only this exact initial normalization and still checks every other field. |
| First zoned timed due on a previously unscheduled item | The app displayed the requested time; due retained its named timezone, and start became the same zoned time. The fix accepts only this exact initial normalization. |
| Change an existing all-day due | September 7 → September 8 verified while the prior September 7 start remained intact. A changed prior start is still rejected. |
| Zoned time on an item with an existing floating start | With and without alarms, this store dropped the requested zone and retained a floating local due. This remains a mismatch, never silently accepted as zoned. v0.6.1 adds an explicit floating input for genuinely local-clock intent. |
| Add a relative alarm | Exact due and -600-second trigger were stored. The GUI showed the trigger time as its primary row time, while the separate Early Reminder control remained unset. Verification does not claim that UI control is configured. |
| Clear due while retaining a relative alarm | Rejected before mutation because the trigger would lose its anchor. |
| Explicitly clear due and all alarms | The GUI date clears, but this store can also strip an existing start timezone. This remains verification pending; the fix does not hide that preservation failure. |
| Zoned DST repeated hour | A separate Foundation conversion confirmed that a selected second occurrence cannot survive NSDateComponents. Python rejects both zoned folds before dispatch, including 30-minute transitions; absolute alarm instants remain available. This is a pure native conversion test, not a GUI notification test. |

## Fix boundaries

The verifier still checks every stable field. Its only new start normalization
is an initially absent due/start becoming the exact observed first all-day,
zoned timed, or floating timed start. It does not excuse changes to an existing start, timezone
loss, alarm loss, recurrence drift, or unrelated text changes.

Floating input is explicit:

```json
{"kind":"timed","floating":true,"local_date_time":"2026-09-08T09:30:00"}
```

It means local wall-clock time, with no fixed timezone or UTC offset. It is not
an automatic retry or a substitute for an explicitly requested zoned instant.

## Final candidate validation

The pre-sign source test selection passed 282 tests, including native/Python
verification parity, the new date inputs, and mutation boundaries. Plugin and
Minis validation passed.

The first signed staging helper (source `1ad0ffbc7d11565c553206ea35ce418e130b9033`)
passed local Developer ID, notarization, exact manifest/file, and protocol
verification. Its full assembly run executed 965 tests; a README copy-edit
fixture was the only failure (one opt-in test was skipped). The fixture was
corrected without changing public-claim checks.

With that staging helper, actual Core calls and GUI observation confirmed:

- Recurring completion returned a no-write unsupported result and left the
  series on September 9, with the same two completed occurrences.
- Updating an existing floating item to 15:45 returned `verified`, preserved
  its prior start and note text, and displayed 15:45 in the app.
- First all-day and first zoned timed patches returned `verified`; the GUI
  displayed September 10 and September 10 at 11:00 respectively.
- First floating timed patch displayed 12:00 and returned the exact intended
  due, but synthesized the same floating start and reported pending. That
  additional observed initial-start form is now covered by the narrow fix.

The final helper source is `47bab1ff8ae7aba9d9dbac0ad49364e05f548826`.
[Preparation run 33969956080](https://github.com/Oscar-V4/apple-reminders/actions/runs/33969956080)
passed all four stages, including 965 tests on Python 3.12 (one opt-in runtime
test skipped), signed-candidate verification, and attestation. The actual three
downloaded files matched the full three-subject SLSA statement and all 13
required workflow certificate identity fields. Local Developer ID, notarization,
manifest/file checks, and protocol probes passed for the universal helper.

The same full 965-test suite also passed locally through a newly extracted and
verified bundled CPython 3.13 runtime in 189.958 seconds, with the assembled
runtime probe enabled and no skipped tests. The strict source and document
mirror audit passed for all 67 packaged files.

Using the final signed helper through the bundled MCP launcher:

- First floating due patch returned `verified`; due and synthesized start both
  matched 13:05, and the app displayed 13:05.
- Direct floating create returned `verified` at 13:20 and the app displayed
  13:20. Replaying the same idempotency key left the active item count unchanged.
- Zoned DST repeated-hour input returned `unsupported_capability` before
  writing; a bounded query found no corresponding test reminder.
- An old duplicate-list receipt returned `ambiguous_scope` with no destination.
- Recurring completion returned `unsupported_recurring_completion` without
  writing; fresh read and GUI still showed the same September 9 occurrence and
  the same completed history.
- A fresh Core launch after the GUI pass exposed nine tools and read lists
  successfully. The actual production Python cache retained all 1,676 files,
  161 directories, hashes/modes and all 11 native signatures.

The four test lists were deleted through the GUI. A bounded Core list read
confirmed all four exact IDs absent, and exact reads of representative main,
recurring, and moved items returned `not_found`. The original list/view was
restored. Recently Deleted was not emptied; synthetic reminders follow the
app's normal recovery period. See [Apple's deletion guide](https://support.apple.com/en-sa/guide/reminders/remna83c9566/mac).
